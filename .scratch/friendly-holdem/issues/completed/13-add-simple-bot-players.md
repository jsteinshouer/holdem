# Add simple bot players

> *This was generated by AI during a grilling session.*

## Parent

`.scratch/friendly-holdem/PRD.md`

## Agent Brief

**Category:** enhancement
**Summary:** Add simple, rule-based computer-controlled bot players that a host can seat in empty seats, so friends can play even when only one or two humans are online.

**Current behavior:**
Every seat must be filled by a human who joins from the private invite link. When only one or two friends are online, the table cannot reach the minimum of two players, or play is thin. There is no computer opponent.

**Desired behavior:**
A host can add simple bot players to specific empty seats between hands. Bots are seated participants that take legal poker actions on their turn using a rule-based strategy, count toward the 2-to-6 seated-player limits and the 2-player minimum to start a hand, and are clearly labeled as bots in every snapshot.

Bot decisions live in a pure, rule-based `BotStrategy` behind a narrow interface. The strategy consumes the bot's own player-specific table snapshot and its legal actions and returns one legal action (fold, check, call, raise, or all-in) with a raise amount when raising. Decisions are based on estimated hand strength (preflop starting-hand strength; postflop made-hand and draw strength via the existing Hand Evaluator Adapter), pot odds, and position, with bounded randomization from a seedable RNG so play is varied but tests are reproducible. There is a single "simple" skill level for now; its tunable constants live in easy-to-change config or constants. Raises are sized as a fraction of the pot (about one-half to three-quarters pot), clamped to the legal minimum raise and the bot's remaining stack. The interface must be substitutable so a later strategy (such as a local model) can replace the heuristic without changing seating, timing, or persistence.

A server-side bot-turn scheduler advances play whenever the current actor is a bot: it applies the bot's chosen action after a short randomized delay of about 0.5 to 2 seconds so humans can follow the table. Bots are exempt from inactivity auto-fold and disconnected-action grace timers; they are never treated as inactive or disconnected. When a bot busts, it sits out like a human and returns only through the existing host rebuy-approval flow.

Bots are added only between hands (no hand in progress) and only by the host, consistent with existing host-power limits: the host cannot alter cards, pots, or hand results. Each bot is assigned a display name from a small curated pool and marked with an `isBot` flag so the client can render a bot badge. Bots take poker actions only and never post chat.

At least one connected human is required to advance play. When no human is connected to a table, the bot-turn scheduler pauses and no new hands start; play resumes when a human reconnects.

Bots are persisted as part of the existing versioned serialized active-table state (including the `isBot` marker and strategy identity). On startup restore, if a bot is the restored current actor, the bot-turn scheduler is re-armed so restored in-progress hands do not deadlock waiting on a participant with no socket.

**Key interfaces:**
- `BotStrategy` — a narrow interface that takes the bot's player-specific snapshot plus legal actions and returns a single legal action (with raise amount when raising). The MVP implementation is a pure rule-based heuristic; the interface must allow substitution without changing seating, timing, or persistence.
- Seedable RNG — a server-owned random source the bot strategy uses, injectable in tests for deterministic behavior.
- Bot-turn scheduler — server-side runtime that detects a bot current actor, waits a short randomized delay, applies the bot's action through the domain layer, pauses when no human is connected, and re-arms after startup restore.
- Domain command for seating a bot — a host-only `addBot` command/payload that seats a bot in a specified empty seat between hands; reuse the existing remove-player and rebuy-approval flows for bots.
- Shared types — add an `isBot` flag to `ParticipantSummary` (flows through `SeatSnapshot`), an add-bot payload, and an `availableControls` entry indicating the host can add a bot.
- Serialized table-state schema — extend persisted participant state with `isBot` and strategy identity so bots restore correctly.

**Acceptance criteria:**
- [ ] A host can add a bot to a specified empty seat only when no hand is in progress, and cannot add a bot when the table is full or a hand is active.
- [ ] Bots count toward the 2-to-6 seated-player limits and toward the 2-player minimum required to start a hand (e.g., one host plus one bot can start).
- [ ] Bot decisions come from a pure `BotStrategy` behind a narrow interface that consumes the bot's player-specific snapshot and legal actions and returns only legal actions.
- [ ] Bot decisions account for estimated hand strength, pot odds, and position; raises are sized as roughly one-half to three-quarters pot and clamped to the legal minimum raise and remaining stack.
- [ ] Bot randomization uses a seedable RNG so a fixed seed produces deterministic, reproducible decisions in tests.
- [ ] A server-side scheduler applies a bot's action after a short randomized delay (about 0.5 to 2 seconds) when the bot is the current actor.
- [ ] Bots are exempt from inactivity auto-fold and disconnected-action grace timers and are never treated as inactive or disconnected.
- [ ] A busted bot sits out by default and returns only through the existing host rebuy-approval flow.
- [ ] Bots are marked with an `isBot` flag in every viewer snapshot, are assigned a curated display name, and never post chat; their actions appear in the public action log like any player.
- [ ] When no human is connected to a table, the scheduler pauses bot turns and no new hands start; play resumes when a human reconnects.
- [ ] Bots persist as part of the versioned active-table state, and a restart mid-hand with a bot as the current actor restores and resumes without deadlock.
- [ ] Bot management is host-only and cannot alter cards, pots, or hand results.
- [ ] Snapshot privacy is preserved: a bot's hole cards follow the same reveal rules as a human player's and are never exposed to other viewers.
- [ ] Automated tests cover bot strategy decisions under a fixed seed, pot-fraction raise clamping, seating between hands, scheduler delay and turn advancement, timer exemption, no-human pause/resume, busted-bot sit-out, and restart-mid-hand resume.
- [ ] Existing unit and end-to-end tests continue to pass.

**Out of scope:**
- Language-model bot strategies, local or external (the interface is added now; a model-backed strategy is a later enhancement).
- Multiple bot difficulty levels, configurable bot personalities, or bot chat and table talk.
- Auto-filling empty seats with bots on hand start, or adding bots mid-hand.
- Bot auto-rebuy or any bankroll change without host approval.
- Changing public realtime event names, snapshot privacy rules, or poker rules beyond what bot support requires.

## Comments

- Design was hardened through a grilling session. Key decisions: rule-based strategy behind a substitutable `BotStrategy` interface (no external API calls); host adds bots to empty seats between hands; busted bots sit out for host rebuy approval; ~0.5–2s randomized action delay; bots persist and auto-resume across restart; play pauses when no human is connected; single "simple" skill level; pot-fraction raise sizing.
- A local small language model was considered for bot decisions but deferred: in the single always-on Node service it adds weight hosting, inference latency, memory pressure, and non-determinism, and a rule-based fallback would be required anyway. The `BotStrategy` seam keeps that path open for later.
